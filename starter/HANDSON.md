# Claude Code ハンズオン手順

## ゴール
「問い合わせに優先度を追加する」変更を、仕様を基準にして安全に実装する。

---

## Step 1：既存コードを調べる
Claude Codeへ次を依頼する。

```text
このSpring Bootプロジェクトを調査してください。

今回、「問い合わせに優先度を追加する」機能を追加します。

以下を整理してください。
・問い合わせデータの構造
・登録 / 一覧表示 / 保存処理
・検索 / ステータス絞り込み処理
・関連するController / Service / Repository
・関連するテストコード

調査結果は、「ファイル名 → 役割 → 今回の機能との関係」の形で整理してください。
この時点ではコードを変更しないでください。
```

### 講師チェック
- コード変更が行われていないか
- Entity / Repository / Service / Controller / Template / Test まで追えているか

---

## Step 2：影響範囲を分析する
```text
先ほどの調査結果をもとに、
「問い合わせに優先度を追加する」影響範囲を分析してください。

【仕様】
・優先度は「高」「中」「低」
・登録時に選択し、一覧に表示する
・優先度で絞り込みできる
・既存の検索 / ステータス絞り込みは維持する

以下を整理してください。
・直接変更が必要なファイル
・影響を受ける可能性があるファイル
・データモデル / DBへの影響
・既存機能 / テストへの影響
・追加すべきテスト

「変更箇所」と「確認箇所」を分けてください。
まだコードは変更しないでください。
```

---

## Step 3：Planをつくる
```text
これまでの調査結果をもとに、「問い合わせに優先度を追加する」実装計画を作成してください。

【仕様】
・優先度は「高」「中」「低」
・登録 / 一覧表示 / 絞り込みに対応する
・既存の検索 / ステータス絞り込みは維持する

【受入基準】
・高 / 中 / 低で登録できる
・一覧表示 / 絞り込みができる
・既存機能が正常に動作する

計画には以下を含めてください。
・変更対象ファイルと変更内容
・影響範囲 / テスト / リスク
・実装する順番

必要最小限の変更とし、まだ実装しないでください。
```

### 講師チェック
Planが次を含むことを確認してから承認する。
- データモデル
- フォーム
- 検索条件
- 一覧・登録画面
- テスト
- 既存機能の回帰確認

---

## Step 4：実装する
```text
先ほど承認した計画で、「問い合わせに優先度を追加する」機能を実装してください。

以下のルールを守ってください。
・計画の範囲だけを変更する
・変更は必要最小限にする
・既存の設計 / 命名規則を維持する
・関係のないリファクタリングは行わない
・既存の検索 / ステータス絞り込みを壊さない

受入基準を確認できるテストを追加し、既存テストも実行してください。

実装後は以下を報告してください。
・変更したファイルと変更内容
・実行したテストと結果
・受入基準の充足状況
・残っている懸念点
```

---

## Step 5：テスト・動作確認
```text
実装した「問い合わせの優先度機能」を検証してください。

【確認対象】
・高 / 中 / 低で登録できる
・一覧に優先度が表示される
・優先度で絞り込みできる
・「すべて」で全件表示できる

【回帰確認】
・既存の検索機能が正常に動作する
・ステータス絞り込みが正常に動作する

関連する自動テストを実行し、不足している場合はテストを追加してください。
最後に、「確認項目 → 結果 → 根拠」の形式で報告してください。
```

---

## Step 6：変更差分レビュー
```text
今回の実装による変更差分をレビューしてください。

【今回の目的】
問い合わせに優先度機能を追加すること。

以下の観点で確認してください。
・Planにない変更が含まれていないか
・仕様と関係のない変更がないか
・不要なリファクタリングがないか
・既存の設計 / 命名規則に沿っているか
・重複や不要なコードがないか
・既存機能を壊す可能性がないか

問題がある場合は、「対象 → 問題 → 理由 → 修正案」の形式で整理してください。
まだコードは修正しないでください。
```

---

## Step 7：受入基準と照合
```text
実装結果を受入基準と照合してください。
SPEC.md の各受入基準について、
「満たしている / 未確認 / 問題あり」のいずれかで判定してください。

あわせて、判定の根拠となるコード・テスト・確認結果を簡潔に示してください。
この時点では追加修正しないでください。
```

---

## Step 8：問題があった場合だけ修正
```text
先ほどのレビュー結果をもとに、確認された問題だけを修正してください。

以下のルールを守ってください。
・問題が確認された箇所だけを変更する
・変更は必要最小限にする
・新しい仕様を勝手に追加しない
・関係のないリファクタリングは行わない
・既存機能への影響を避ける

修正後は、関連するテストと既存テストを再実行してください。
```

---

## Step 9：最終レビュー
```text
今回の変更について最終レビューをしてください。

【目的】
問い合わせに優先度機能を追加すること。

以下を最終確認してください。
・仕様を満たしているか
・受入基準を満たしているか
・計画通りの変更になっているか
・既存機能への回帰がないか
・不要な変更が含まれていないか
・残っているリスクや懸念点がないか

追加のコード変更は行わないでください。
```

---

## Step 10：PR説明文を作る
```text
今回の変更内容を、レビュー・引き継ぎ用に整理してください。

【目的】
問い合わせに優先度機能を追加すること。

以下をまとめてください。
・変更の目的
・変更した主なファイル
・実装した機能
・仕様上の重要なポイント
・実施したテストと結果
・既存機能への影響
・残っている懸念点

専門的すぎない表現で、Pull Requestの説明文として使える形にしてください。
コードの追加変更は行わないでください。
```
